# Пункт 8 — безопасная одноразовая привязка Windows MCP

Дата: 19.11.2026. **Реализовано и проверено локально; рабочий Worker v11 НЕ изменён.**

## Протокол

1. При установке **на самой Windows-машине** `src/windows/device-identity.mjs` генерирует Ed25519 keypair. Приватный PKCS#8 хранится только на этом ПК; установщик (пункты 15–16) обязан выставить ACL владельца и службы. Ни один приватный ключ, идентификатор уже привязанного устройства или готовый токен не попадает в архив/GitHub.
2. Клиент обращается к `POST /device/pair/start` по HTTPS, передавая только публичный ключ и метку. Cloudflare возвращает **10-символьный случайный код**, локально сверяемый fingerprint (первые 16 hex SHA-256 от base64url-кодированного публичного ключа), случайный `request_id` и срок 600 секунд.
3. Владелец открывает `/device/pair/manage`, сверяет код и fingerprint с экраном ПК, вводит существующий пароль владельца. Защита: Origin/Sec-Fetch-Site, одноразовый 256-битный CSRF proof, общий с OAuth лимит пароля 5/15 минут, TTL 600 с. Повторное подтверждение кода невозможно.
4. `POST /device/pair/status` по непредсказуемому `request_id` возвращает только `pending` или `approved` и новый `device_id`; без приватного ключа его знание не даёт доступа.
5. При каждом успешно OAuth-авторизованном запросе `/mcp` Worker сначала отправляет на **фиксированный Workers VPC** адрес `GET http://127.0.0.1:8765/device/attest` новый 256-битный nonce и device id. Windows MCP должен подписать строку `QWEN-MCP-DEVICE-V1\n<issuer>\n<device_id>\n<nonce>` ключом устройства; Worker проверяет Ed25519 по ключу из прежнего Qwen Durable Object. Отсутствие пары, origin, неверная подпись и replay — fail-closed 503, до вызова MCP-команды.
6. На той же странице `/device/pair/manage` владелец с паролем, CSRF proof и точным `device_id` отзывает доступ. Проверка текущей пары повторяется после attestation; при замене пары прежний ключ перестаёт работать. После обычной перезагрузки прежняя подтверждённая пара сохраняется в DO; одноразовая регистрация не повторяется.

## Границы реализации

- В репозитории есть **cloud route, durable storage, обязательная подпись origin и Windows Ed25519 helper**, но нет ещё готового Windows MCP HTTP runtime (`/device/attest` реализуется в пункте 10), безопасного сохранения приватного ключа системным установщиком и локального GUI/CLI первичной привязки (пункты 15–16).
- **На рабочую v11 не выкладывать этот код до готовности Windows MCP**: новый Worker требует зарегистрированный и подписывающийся origin и закономерно вернёт `503 device_not_paired` всем ChatGPT клиентам, если опубликовать его преждевременно.
- Один активный `device_id` для выделенного Qwen Tunnel. При тестах на ПК владельца и последующей установке у друга **каждая машина генерирует собственный ключ**; повторное одобрение новой пары отзывает прежнюю. Не копировать секреты тестового ПК в финальный архив.
- Собственный ПК владельца подключаем только **после завершения разработки** на отдельном этапе комплексной приёмки, а не после каждой правки.

## Проверки

`npm run check`, `npm test`, `CI=1 WRANGLER_SEND_METRICS=false npm run build` (dry-run). Тестируются реальная SQLite DO-перезагрузка, подтверждение владельца/пароль, mismatch fingerprint, повтор/истечение CSRF, поддельный Origin, повторный pairing code, отзыв, отсутствие пары, поддельная подпись, устаревший nonce, выключенный origin; прежний OAuth + PKCE и весь MCP набор регрессий.

**Итог:** исходники и автоматические тесты — подготовлены; живое end-to-end подтверждение Windows и ChatGPT запланировано на комплексную приёмку. Пункт 8 не отмечать полностью закрытым до готового Windows HTTP origin и установки.
